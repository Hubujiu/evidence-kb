# SQLite connection bootstrap admission

The ordinary concurrent-service migration contract exposed SQLITE_BUSY while changing journal mode, before the migration transaction had begun. A migration lock cannot protect an earlier connect callback. SQLite may return BUSY without waiting when waiting would deadlock; a WAL database can also be briefly busy during last-connection cleanup. See the official [busy-handler contract](https://www.sqlite.org/c3ref/busy_handler.html) and [WAL section 9](https://www.sqlite.org/wal.html).

The connection owner probes the current mode, changes it only if necessary, closes each cursor, and confirms the requested result before publishing a configured connection. Only SQLITE_BUSY during these idempotent journal-mode statements permits another admission attempt. One absolute deadline bounds all statements and waits; each potentially blocking statement receives only the remaining native busy-timeout budget. Non-BUSY errors and mismatched returned modes fail immediately. FULL, foreign keys, recursive triggers and the ordinary 30-second busy timeout are configured before success. This protocol never retries business transactions or COMMIT_UNKNOWN. Legacy explicit-file stores retain DELETE/NullPool and create no bootstrap sidecar.

`SQLiteBootstrap` abstracts one new connection and environmental contention. Both managed WAL and legacy DELETE targets are explored. The environment may produce BUSY or complete the requested mode while the initializer waits. The positive checks configured-before-publish, BUSY-only retry, and non-resetting budget. Three controls inject premature publication, retry of other errors and budget reset; two witnesses reach retry success and exhausted BUSY failure.

Bounds are two abstract waiting ticks and at most three attempts, not a measurement or proof of real elapsed time. Actual per-statement deadline accounting and cursor release are tested in deterministic implementation contracts and guarded by source lint. The model does not assert every connection must succeed: persistent contention fails admission. Filesystem faults, arbitrary mode changes after publication, process scheduling and SQLite implementation refinement remain outside the model. No failure is hidden by retrying a test run.
