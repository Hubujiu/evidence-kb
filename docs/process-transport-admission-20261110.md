# 进程插件启动与关闭的状态边界

审查基线：`f0ea7450b33b21022fbb61e91c1539d5a290c89b`。

## 已复现的问题

`ProcessTransport` 的状态分散在 `_process`、`_closed`、`_draining` 和 I/O
线程字段里。原来的 `start()` 只检查是否曾创建过进程，没有检查关闭是否已经开始。

因此，`close(); start(); close()` 可以在关闭后创建进程。握手随后因为 transport
不可用而失败，第二次 `close()` 又因为 `_closed` 为真直接返回，失去新进程的清理
路径。关闭已开始但清理尚未结束时，也存在同样的启动准入缺口。

使用当前生产类和模拟的 `Popen` 实际复现了这条路径：关闭后的进程创建次数为 1，
终止次数为 0。没有启动真实进程，也没有证明正常挂载流程曾触发此问题。

## 修改与状态规则

`start()` 现在在同一个生命周期锁内、调用 `Popen` 之前，拒绝 `_closed` 或
`_draining` 的实例。已经启动过的实例仍返回 `PROCESS_ALREADY_STARTED`；尚未启动但
已关闭或正在关闭的实例返回既有的 `PROCESS_UNAVAILABLE`。

| 当前状态 | 操作 | 行为 |
| --- | --- | --- |
| 新建且开放 | start | 创建进程并继续原有握手 |
| 已创建进程 | start | 拒绝重复启动，保持原错误码 |
| 新建且开放 | close | 进入关闭，完成资源清理 |
| 关闭已开始、清理未结束 | start | 创建进程前拒绝 |
| 已关闭 | start | 创建进程前拒绝 |
| 已关闭 | close | 保持原有幂等行为 |

这条规则让“关闭”成为不可逆的准入边界，减少调用者和代理对对象是否还能启动的猜测。
现有请求回执、UNKNOWN 处理、握手、清理重试和插件替换协议没有改动。

## 有限模型与回归

- 新的 `ProcessTransportAdmission` 模型只覆盖一个 transport 和最多一次进程创建。
  模型区分启动、关闭准入、实际进程停止和关闭结果发布。
- 正模型检查关闭开始后不再创建进程、关闭后没有运行进程、运行进程有所有者、关闭
  状态继续拒绝准入。
- 两个负控恢复原来缺失的准入守卫，分别违反 `NoSpawnAfterDrain` 和
  `ClosedOwnsNoRunningProcess`。这两个负控对应本次实际复现的旧行为。
- 两个行为合同在旧实现均失败，在修改后通过。并发合同用 Events 暂停关闭清理，
  直接验证关闭尚未完成时启动就已被拒绝；没有用 sleep 建立顺序。
- 将 `ProcessTransport.start` 加入源码绑定；它此前未被通用状态字段发现器识别。
  必需结构检查也拒绝删除该守卫的错误变体。
- 新增 `combination-inputs-process-v7.json` 保存本次精确增量，原 v1–v6 清单保持不变。
  所有既有运行定义、模型文件、合同身份和共享入口约束继续保留。
